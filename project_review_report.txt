1. BRIEF INTRODUCTION AND FINALIZED PROBLEM STATEMENT

VoltPulse is a web-based electric vehicle charging platform intended to help EV users discover nearby charging stations and, in later phases, reserve chargers and track charging sessions. The project combines a responsive React frontend with a FastAPI backend and a local PostgreSQL database.

Finalized Problem Statement:
EV users need a single, secure, and convenient system that can display nearby charging stations, show charger and connector availability, provide location-aware search, support user authentication, and create a foundation for reservations and charging-session management. The proposed system addresses this need through a modular web application with authentication, station discovery, map visualization, and database-backed charging-domain APIs.

2. PROJECT OBJECTIVES AND PROPOSED SOLUTION

Objectives:
- Provide secure user registration and login.
- Protect authenticated application areas from unauthorized access.
- Store EV charging domain data in a structured local PostgreSQL database.
- Display charging stations with valid coordinates, charger status, connector types, and price information.
- Allow users to search stations by name, address, or city.
- Detect the user's location and sort stations by proximity.
- Present station information in both map and list views.
- Establish backend APIs for operators, stations, chargers, connectors, reservations, and charging sessions.
- Keep the architecture modular so future reservation and payment features can be added without redesigning authentication.

Proposed Solution:
The solution uses React 19, Vite, TypeScript, Tailwind CSS, Leaflet, and Lucide icons on the frontend. FastAPI, SQLAlchemy, Pydantic schemas, JWT authentication, password hashing, Google OAuth support, and PostgreSQL are used on the backend. Supabase is currently used for authentication-related frontend support, while the business-domain data is designed for local PostgreSQL integration.

Authentication flow:
1. The user registers or logs in.
2. The backend validates credentials and creates a JWT.
3. The frontend stores the authenticated session state through AuthContext.
4. ProtectedRoute permits access to the dashboard only for authenticated users.
5. The backend uses the JWT to identify the current user for protected operations.

4. LOGIC BUILDING / ALGORITHM / METHODOLOGY

Station discovery methodology:
1. Request the user's browser location when the dashboard loads.
2. If permission is denied or unavailable, use a default map center and allow manual city search.
3. Request station data from GET /api/stations.
4. Validate station structure and latitude/longitude ranges.
5. Flatten charger connector data for each station.
6. Calculate available charger count, connector types, minimum available price, and status summary.
7. Calculate distance using the Haversine formula when user coordinates are available.
8. Filter records using station name, address, or city search text.
9. Sort the resulting stations by distance.
10. Render the same station data in list and Leaflet map views.

Authentication methodology:
- Normalize email addresses before lookup.
- Hash passwords before storage.
- Verify credentials before issuing JWT access tokens.
- Support Google identity login through OAuth redirect and Google ID token flows.
- Link an existing local account to a Google identity when email addresses match.
- Use protected route handling on the frontend and current-user dependency handling on the backend.

Data methodology:
- Use UUID primary keys for domain entities.
- Define relationships between operators, stations, chargers, connectors, users, reservations, and sessions.
- Load station chargers and connectors efficiently for station responses.
- Reject or omit invalid station coordinates before map rendering.

11. CHALLENGES FACED AND SOLUTIONS IDENTIFIED

Challenge: Combining authentication with a separate business database.
Solution: Keep authentication concerns in AuthContext and dedicated auth modules while keeping stations and charging operations in the FastAPI/PostgreSQL layer.

Challenge: Browser location permission may be denied or unavailable.
Solution: Provide a default map center, visible status feedback, a retry action, and manual search.

Challenge: Invalid or incomplete station coordinates can break map rendering.
Solution: Validate coordinate type, finiteness, and geographic bounds in the backend and frontend before rendering.

Challenge: Station data contains nested chargers and connectors.
Solution: Use SQLAlchemy relationships and eager loading, then map nested API data into a typed StationData model.

Challenge: Users need both geographic and textual station discovery.
Solution: Combine Haversine distance calculation, proximity sorting, city/address/name filtering, and Leaflet visualization.

Challenge: Reservation behavior is not fully connected yet.
Solution: Keep the interface and route intent visible through a reservation stub while reserving persistence, conflict checking, and payment for the next development phase.

Challenge: Local environment configuration differs between machines.
Solution: Use environment variables for backend and frontend service configuration and document PostgreSQL, Supabase, and development server setup.
